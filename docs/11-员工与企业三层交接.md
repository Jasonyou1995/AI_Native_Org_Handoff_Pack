# 11 · 员工与企业三层交接

> 状态：架构提案，不是已实现的三层产品。当前代码只有单进程的本地/云端隐私网关。下面的跨主体身份、授权继承、撤销、企业收件和两跳审批尚未端到端实现。现有范围见 [网关规范](../spec/PRIVACY-GATEWAY-SPEC.md)，提案契约见 [三层规范](../spec/THREE-TIER-SHARING-SPEC.md)。

## 一句话

**个人助理保留方法，企业助理接收获准成果，云端只处理再次缩减的子任务。**

这不是把员工知识库逐层上传，也不是把三个模型简单串起来。它把“完成工作”和“交出全部个人经验”分开：每跨一道信任边界，都重新确认目的、必要内容、接收者和是否允许再转发。员工对经验被复制的担忧是设计动机，不是已经验证的普遍事实，更不是技术能保证不会失业的承诺。

## 三层分别做什么

| 层 | 可以看什么 | 做什么 | 不默认获得什么 |
|---|---|---|---|
| 员工设备与个人本地模型 | 在明确治理边界内的个人笔记、工作输入、个人方法 | 本地推理，提炼可交付成果，预览并批准 | 不自动同步完整记忆、个人知识库或处理过程 |
| 企业内网网关与企业本地模型 | 员工批准交付的必要事实、企业有权处理的业务资料 | 业务计算、规则核对、组织协作，准备第二份更小的云任务 | 不获得员工私人原文、私人映射表或隐含的再转发权 |
| 经批准的云模型 | 第二次独立批准后的最小任务与必要上下文 | 本地能力不足时提供写作、分析等辅助 | 不获得个人知识库、完整企业资料或两层还原映射 |

```text
Employee device: private context -> approved deliverable
    [employee release approval + company acceptance policy]
Company gateway: authorized deliverable + company context -> reduced cloud task
    [inherited onward permission + independent company cloud approval]
Cloud: bounded subtask -> company validation and combination
Company result -> employee optional local restoration -> reviewed final output
```

“本地”必须说明相对谁本地。企业内网模型不是员工私人模型。若员工把原文直接交给企业部署的现有网关，企业网关就已经接触原文，不能事后称为员工隐私保护。设备端预处理必须发生在第一跳之前。

## 先分资料类别，不擅自判产权

1. **个人资料与个人方法**：在合法、获准的设备环境中默认不离开设备。职务相关方法的归属有争议时，不能仅凭员工标签断言为个人所有。
2. **雇主拥有或有权管理的工作资料**：按合同、适用法律和组织制度处理。不能借“个人本地”隐藏、侵占或拒绝依法应交付的企业资料。
3. **批准共享的交付物**：只授权约定用途和范围；共享副本不自动转移全部知识产权，也不意味着允许训练、入知识库或再转发。
4. **混合或权属不明**：默认不外发，先由有权限的人厘清，不能让模型替代权属判断。

存储地点不决定法律所有权。公司管理的笔记本可能有管理员、终端监测、备份和日志；本方案不声称能对设备管理员保密。确需个人边界，须有透明的设备、密钥、账号和管理制度，而不是隐藏文件夹。ICO 的英国工作场所监测指导强调透明度与必要性，不能把它当作所有地区统一的法律结论。[ICO 工作场所监测指导](https://ico.org.uk/media/for-organisations/uk-gdpr-guidance-and-resources/employment/monitoring-workers-1-0.pdf)

## 两道门，不是一次同意永久放行

- 员工批准第一跳的**确切交付内容、目的和企业接收者**；允许企业内部使用与允许向云端转发是两个独立选择。默认禁止 onward sharing（继续转发）。
- 企业政策只能进一步收紧员工已授予范围，不能由管理员扩大。若云端有必要但原授权禁止转发，应请求新的明确授权，或在企业本地完成，不能改标签绕过。
- 企业生成的衍生摘要仍继承来源限制。添加企业资料不洗掉员工限制；混合来源取权限交集。
- 云端门再次检查、脱敏并批准**第二份确切请求**，包含系统提示、正文、参数、目标与模型。员工允许转发不等于企业已经批准发送。
- 委托范围只能缩小，到期不能延长，每次使用都检查撤销。撤销阻止后续受控使用，不能召回已发送、复制或被人记住的信息，也不能保证抹除模型训练影响。
- 提交材料及模型输出都是数据，不是权限命令。模型只可建议阻断，不能批准外发。

审批信封至少记录 `purpose`、`dataOwnerClass`、`destinationAllowlist`、`onwardSharing`、`expiresAt`、`contextRefs`、`labeledEvidence` 和批准绑定。`contextRefs` 是受接收者自身权限限制的引用，不是读取个人库的通行证。证据区分事实、推断和待核验项，只承载批准的摘要或引用，不收集私人思考链或模型内部 chain-of-thought（思维链）。

receipt（批准凭据）仅携带或引用不可伪造的绑定元数据，不放个人正文、笔记、映射或个人上下文。哈希与标识也可能暴露关联信息，应限制访问和保留，不能称为匿名。身份认证、企业接收权限与员工批准权必须分别验证，单个共享 bearer token 不足以实现跨员工隔离。

## 一个纯虚构的报价例子

1. 销售 alice 在设备上保留个人沟通笔记与谈判方法。本地助理提炼“产品 A、10 件、下周交货”的必要事实。
2. alice 只批准这些事实进入企业，用于本次报价，并单独允许向指定云模型提交无身份的文案子任务。客户身份若企业确有必要接收，应作为第一跳中明确批准的字段，而非默认附带。
3. 企业本地系统结合自己的价格表计算价格与可交付日期。个人笔记仍不进入企业，企业价格表也不进入云端。
4. 企业另行批准云请求：“为产品 A 的报价写一段礼貌说明，保留 PRICE 和 DATE 占位符。”无客户身份、底价、折扣逻辑或私人谈判策略。若此子任务本地可完成，就不调用云端。
5. 云返回文案，企业校验后在企业内填回价格和日期，把结果交给 alice。
6. alice 可在自己的设备内补充私人称呼或沟通风格；补回后的内容不自动再次上传。发送给客户是另一个需获准的动作。

## 效率与利益怎么兼顾

- 不建全员共享的私人记忆库。每跳只处理有界请求，每个请求、用户和组织限制字节、并发、排队数、时长与预算，满载时背压拒绝，不以云端偷偷兜底。
- 本地能做的不必上云；更大模型是否有价值用任务成功率、总时延、成本和披露量验证。三层也可能增加等待与审批成本，不保证无限扩展或必然更快。
- 企业可按获准成果的质量、贡献和协作效果认可员工，提供自愿、单独授权的知识贡献机制，而不是用私人全过程、个人笔记或内部思维链进行绩效采集。
- 可讨论贡献署名、奖金、培训和清晰的再利用条款，作为建立信任的制度建议，不保证收入、岗位安全或商业成功。

设计遵循目的必要的最小化方向。NIST 的 minimization 定义强调与合法授权目的相关且必要的个人信息处理与保留；它不证明本产品合规或不泄露。[NIST 最小化定义](https://csrc.nist.gov/glossary/term/minimization)

## 验证顺序与非目标

先用合成数据验证：禁止转发不可绕过、目的/目标/期限不可扩张、每跳批准精确绑定、撤销与重放拒绝、跨员工隔离、引用越权失败、无私人正文日志、异常不外发、满载背压。再评估部署身份体系、终端管理员边界、供应商留存、人员制度和真实任务效果。当前测试不能冒充这些尚未完成的验证。

不替代知识产权或劳动争议判定，不提供法律意见，不保证防止裁员、零泄露、独占个人经验、通用性能或对所有模型有效。合规、保留和法定义务可能与自选分享偏好冲突，应透明处理并获得专业审查，不能用此协议规避义务。
