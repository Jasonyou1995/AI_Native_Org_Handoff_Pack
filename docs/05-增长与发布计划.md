# 05 增长与发布计划

> 一句话故事：这个仓库不是「一个交接库」，它是**测量协同成本的尺子**。库让人用一次，尺子让人引用一年。

本文件回答四个问题：给谁看、怎么让人三十秒内懂、三分钟跑通、为什么愿意 star。它不回答「怎么写代码」，那是 `docs/01-工程计划.md`。

---

## 1. 定位

**英文 slogan（README 第一行）**

> The coordination-cost benchmark for agent-mediated organizations.

**中文对应**

> 智能体中介组织的协同成本基准。

选这三个词的原因：**benchmark** 区别于 library（库是工具，基准是标准，标准才有引用和社区）；**coordination-cost** 区别于 efficiency（efficiency 是个模糊的高效词，coordination cost 是个有分解的构念）；**agent-mediated** 区别于 AI organization（前者精确且不过度声称）。

反面口号，明确不要用：「The best handoff middleware」「Fastest agent orchestration」。这类口号在 HN 上零转化，因为它不承诺任何可验证的东西。

**一个核心判断**：星标不是目标，**被引用的尺子**是目标。GitHub star 是路径上的一个中间指标，真正的复利来自两处：一是被论文引用，二是别人用 CCI 分数讨论自己的架构。第二处只有榜单能做，见第 5 节。

## 2. 目标人群

三类人，动机完全不同，打法完全不同。**不要用同一份 README 同时讨好三个人**，README 是给第 1 类写的，第 2、3 类各有入口。

### 人群 1：做 agent 编排的工程师（star 的主要来源）

| 项 | 内容 |
|---|---|
| **他们是谁** | 在 LangGraph / AutoGen / CrewAI / 自研 agent 框架里做多智能体流水线的工程师，技术判断力强，对「营销话术」零容忍 |
| **他们现在的痛** | 多智能体流水线的账单和延迟不可预测；跨 agent 交接出错时无法定位是发送方没写清楚还是接收方理解错；出问题时没有可比较的基线，只能凭感觉改 prompt |
| **他们关心什么** | 花钱、延迟、失败率。**不关心** Williamson，不关心效应量 |
| **打动他们的第一句话** | `npx handoffpack bench --demo`，30 秒出你自己的三臂成本对比图 |
| **打动他们的证据** | 我们**自己**的数字。真实 run 数、真实 token 数、真实美元数。我们自己的 `C` 臂比 `F` 臂贵，这一点主动写出来，比只报好消息可信十倍 |
| **他们会 star 的条件** | 三分钟能跑通；有 Docker 一键路径；有可复现的种子；README 里的数字能追溯到论文 |
| **他们不会 star 的行为** | 首屏放徽章墙；把论文摘要贴在首屏；要求填表才能看到 demo |
| **成功判定** | 30 天内，来自「非关注者」的 star ≥ 150；`--demo` 的周活独立用户 ≥ 30 |

### 人群 2：做 AI 组织研究的学者（引用的主要来源）

| 项 | 内容 |
|---|---|
| **他们是谁** | IS / OM / 组织理论 / 人类与 AI 协作方向的博士生与教职，习惯看 Organization Science、ISR、CIST、ICIS、MISQ |
| **他们现在的痛** | 「AI 会改变组织」这句话说了五年但没有可测量的构念；agent 侧的实验测 token 与准确率，无法支撑组织层面的推论；复现门槛高到没人复现 |
| **他们关心什么** | 构念效度、预注册时点、ground truth 独立于被测系统、效应量、异质性、威胁到效度 |
| **打动他们的第一句话** | 「我们的三个臂携带**逐字节等价**的信息，自由文本由纯函数从结构化包渲染生成。」这一句直接回应他们最大的疑虑 |
| **打动他们的证据** | OSF 预注册链接、`numbers_manifest.json`、`verify_numbers.py`、开源权重的可复现子集 |
| **他们会 star 的条件** | `spec/` 三份规范本身可读可引用；贡献指南明确允许 AI 辅助贡献 |

### 人群 3：要做 agent 组织治理合规的企业（长期可信度来源）

| 项 | 内容 |
|---|---|
| **他们是谁** | 大企业的 AI 治理、风险、内控、法务团队。他们的问题是「agent 越权了怎么证明它没越权」 |
| **他们现在的痛** | 审计证据不足：agent 的每一次能力调用都要人工复核，因为自由文本交接无法证明边界；出了事拿不出可审计的轨迹 |
| **他们关心什么** | 强制执行的 scope、每次使用的撤销检查、可验证签名、可导出的审计日志 |
| **打动他们的第一句话** | 「越界调用不是被劝阻，而是**调用失败**。」`C` 臂的能力令牌让边界违规变成签名错误而不是纪律问题 |
| **打动他们的证据** | ACM Artifact Review 的 Functional + Reusable 徽章；`spec/HANDOFF-PACK-SPEC.md` 的七条规则与十个验收场景；`c_blocked_by_enforcement`（只有 `C` 能报，能力差异而非得分差异）与 `s_blocked_by_policy`（模型自己守规矩）的分开计数 |
| **关键判断** | **不要在 GitHub 上追这个人群。** 他们的转化周期以季度计，star 换不来。追他们只能通过论文的治理章节与工件徽章 |
| **成功判定** | 24 个月内，至少一家企业的合规或内控文档引用本项目的 spec 或工件 |

### 3.1 首图选哪一张（决策）

选**堆叠成本成分柱状图**，不选总成本对比图，不选雷达图，不选 Sankey。

| 候选 | 为什么淘汰 |
|---|---|
| 总成本柱状图 | 三臂的总成本差异可能很小甚至看不出来，视觉上等于「没有故事」，也会误导读者以为总量是结论 |
| 四成分堆叠柱状图 | `C_adapt` 在 `C` 臂上按构造归零，把它堆进总高度会让人以为「C 的适应成本被优化掉了」，而那其实是网关把它挡掉了。**首图只堆三个可比成分** |
| CCI 雷达图 | 四轴可比性不直观，且 CCI 是标量，雷达图会把它伪装成四维结构 |
| Sankey / 流程图 | 展示的是系统结构，不是发现。系统结构属于 `spec/`，不占首屏 |
| **四成分堆叠柱状图** | **它一眼说明「总成本相近，成分不同」，这正是本文的论点。若某臂总成本确实差异明显，在图上再加一条总成本折线作为第二面板** |

图的硬约束：不依赖颜色单独区分臂（用直接标注 + 纹理兜底，色盲可读）；PNG 与 SVG 都出；SVG 控制在 200 KB 以内，GitHub 首屏加载不卡。

### 3.2 30 秒 GIF 拍法

**硬约束**：不超过 12 秒，文件不超过 3 MB，无声，GIF 而非视频（README 首屏自动播放，视频要用户点一下，动起来的机会少一半）。

分镜表，每格标注秒数：

| 时间 | 画面 | 说明 |
|---|---|---|
| 0.0 到 1.5 | 终端，`$ npx handoffpack bench --demo`，回车 | 一条命令 |
| 1.5 到 4.0 | 三臂依次跑完，进度条与实时 token 计数滚动 | 让人看到「它在算」，不是「它在假装」 |
| 4.0 到 7.0 | 终端打印四成分分解表，F / S / C 三列并排 | 核心信息：同样的总成本，不同的成分 |
| 7.0 到 9.5 | 切到 C 臂的运行日志：一条越界调用被拒，`action not in scope`，进程不崩 | 这是 F/S 臂做不到的事，也是承诺机制的直观证据 |
| 9.5 到 12.0 | 回到终端，$ 提示符，打印一行 `full report: docs/…`，光标停住 | 收尾，把人送到 README 的下一节 |

**拍法要求**：终端字号放大到 24 以上，背景用深色，录制时用 `asciinema` 或 `agg` 再转 GIF（保证字体清晰，不受窗口缩放影响）；每一格之间用 0.15 秒硬切，不用转场特效。**不许配字幕条**，字幕会让人以为听不到声音也能懂，但实际没人读字幕。

**验收标准**：把 GIF 单独发给一个没读过文档的人，问「这是干嘛的」，他能答出「在比较三种交接方式的成本」。答不出就重拍。

### 3.3 三分钟上手怎么走通

```bash
# 路径一：Node（最快）
npx handoffpack bench --demo

# 路径二：Docker（环境可复现，推荐给 CI 与不信任本机环境的人）
git clone https://github.com/<org>/handoffpack && cd handoffpack
docker compose up demo
```

README 的上手小节必须明确写四件事，每件一行：

1. **跑完你会看到什么**：一张三臂四成分的对比表，和一张图。
2. **大概多久**：默认任务 3 分钟内出结果（`--demo` 用 T0 与 T1）。
3. **大概花多少钱**：默认 **0 美元**（`--demo` 全部走本地 stub）。要跑真实模型需要 API key，明写预估单价与 `make bench-full` 的量级。
4. **换成你自己的任务怎么换**：给一个 `--task <path>` 的最小例子，两行 YAML。

第 3 条尤其重要。工程师看到「要花钱」会关掉页面，看到「这一步 0 美元」会点下去。**默认值必须是免费的，付费是进阶路径。**

## 5. Coordination Cost Index (CCI)

CCI 的定位一句话：**把协同成本压成一个可比较的标量，让不同的人、不同的协议、不同的仓库能在一个榜单上对话。**

它**不是**论文的主统计量。论文用混合效应模型报成分级的效应量与置信区间，CCI 只服务于社区比较与榜单排序。把标量当论文主指标会把我们变成第 5 节里批评的 CS 侧工作，这一点必须写在 CCI 规范的第一行。

### 5.1 公式

沿用 `spec/COORDINATION-COST-SPEC.md` 的口径并展开：

```
cost_per_success_c = (所有 run 的成分 c 成本之和) / (成功 run 数)

CCI = 100 * sum_c weight_c * normalize_c(cost_per_success_c)
```

其中：

| 符号 | 含义 | 取值 |
|---|---|---|
| `c` | 成本成分 | `search` `spec` `coord` `adapt`（`COORDINATION-COST-SPEC.md` 定义） |
| `weight_c` | 成分权重，**结果看到之前固定并公布** | 见 5.2 |
| `normalize_c` | 归一化函数 | 见 5.3 |

### 5.2 三种权重方案与默认选择

| 方案 | 权重 | 排名含义 | 风险 |
|---|---|---|---|
| **CCI-C（默认，榜单主榜）** | 三个所有臂都能测的成分等权：`search` `spec` `coord` 各 1/3，`adapt` 权重 0 | 「事前成本」排名 | 不测承诺带来的收益，会让 `C` 臂看起来吃亏 |
| CCI-Full（副榜） | 四成分等权，各 1/4 | 「完整协同成本」排名 | **`adapt` 在 `S` 臂与 `F` 臂上的含义与在 `C` 臂上不同**：`C` 臂的越界被构造阻止（见 `docs/04-论文计划.md` 第 6 节 A2）。混在一个标量里是循环论证 |
| CCI-Adapt（诊断榜） | 只有 `adapt` | 「事后适应成本」诊断 | 单成分，易被噪声主导，只作诊断不作排名 |

**默认建议**：榜单主榜用 **CCI-C**，因为三臂都可测、方向一致、不含构造性零。CCI-Full 与 CCI-Adapt 作为并列显示的诊断列，让读者自己看三维，不用我们替他们加权。

权重敏感性必须公开：在权重单纯形上取网格（例如步长 0.1 的 66 个点）重算排名，报告「前三名在多少比例的权重配置下不变」。若第一名在超过一半的权重配置下会变，榜单首页必须写明「排名对权重敏感」。**这是 CCI 唯一诚实的做法，也是一个很强的诚实信号。**

### 5.3 归一化与可比性

```
normalize_c(x) = x / median_c(anchor_suite)
```

`anchor_suite`（锚点套件）是一个**固定的任务集合**，定义如下：

| 项 | 设计 |
|---|---|
| 内容 | 固定 3 个任务：T1 博弈收敛、T2 软件交付流水线、T3 长文档简报，各固定 10 个种子 |
| 版本 | `cci-anchor-v1`，**永不原地修改**。改了就是 `v2` |
| 参照值 | 在锚点套件上跑一次全部臂，取每个成分 `cost_per_success` 的中位数作为除数 |
| 锁定时机 | **看到本文主结果之前**计算并公开，写进 OSF 预注册 |

三条可比性规则，缺一不可：

1. **同一版本**：任何两个提交必须在**同一个** `anchor_suite` 版本与**同一组模型快照**下测过才能直接比较。榜单每行必须显示它测的是哪个 anchor 版本。
2. **同一重测窗口**：提交上来的不是结果，而是**协议 + 实现**。CI 在榜单维护者的重测窗口里重跑你的实现，产生榜单分数。这从根上杜绝了「自己跑一遍贴个数字」。
3. **三货币并列**：CCI 用 token 计算，但每行同时显示 USD 与墙钟秒。三个货币不一致的行标一个警告标记。

### 5.4 榜单页怎么做

GitHub Pages，静态站点，数据来自仓库里 `leaderboard/submissions/*.json`（每个提交一个文件，PR 合入即生效）。

页面结构：

| 区块 | 内容 |
|---|---|
| 顶部 | 一句话说明 CCI 是什么 + 「你在这里排名多少」的自查输入框（输入仓库地址） |
| 主表 | 列：排名、提交名与链接、CCI-C（↓越好）、CCI-Full、CCI-Adapt、成功率、`cost_per_success` 的 token / USD / 秒三列、anchor 版本、模型快照、重测日期、权重敏感标记 |
| 图 | 主表上方一张散点图：横轴 CCI-C，纵轴成功率。**目标是左下角**（既省又准）。把人引到右上角（省但不准）的设计会被刷榜 |
| 「测你自己的」 | 一条 `npx handoffpack cci --submit` 命令与三行说明 |
| 规则与反作弊 | 完整规则摘要 + 违规案例（**公开已剔除的提交与原因**，这是防作弊最有效的手段） |
| 版本历史 | 每个 anchor 版本的排名快照，跨版本排名不直接比 |

### 5.5 社区怎么提交

```bash
npx handoffpack cci --init my-protocol     # 生成 submission.json 模板
npx handoffpack cci --run                  # 本地跑锚点套件，预览分数
npx handoffpack cci --submit               # 提 PR，只改 leaderboard/submissions/<handle>.json
```

提 PR 后 CI 做的事：重跑锚点套件 → 重算 CCI → 与提交的 JSON 比对 → 不一致则 CI 红。**这是唯一的真源**，本地分数只是预览。

### 5.6 防刷榜：六条硬规则

| # | 规则 | 堵住的攻击 |
|---|---|---|
| 1 | **CI 重测**。分数由维护者的 CI 重跑产生，不由提交者提供 | 直接填假分 |
| 2 | **审计日志哈希入提交**。每个 run 的 transcript 生成 SHA-256 摘要写进 submission JSON | 事后换掉实现 |
| 3 | **成功率为 0 的提交不排名，标 `unranked`**（按 `COORDINATION-COST-SPEC.md` 的规则 1：成本不是零，是无穷） | 用「什么都不做」刷低成本 |
| 4 | **撞轮次与超时按满分成本计**，不允许剔除 | 反复重跑直到跑出一个好结果（seed 搜索） |
| 5 | **发布节奏抽查**。维护者在提交 merge 后 30 天内随机抽查 2 个提交的源码与 benchmark 时的 commit 一致性 | 先过审后改实现 |
| 6 | **公开剔除记录**。每一个被剔除的提交、原因、日期都进榜单页 | 让规则变成真的 |

榜单的**长期健康指标**：外部提交数 / 提交被剔除率（理想值 < 10%）/ 提交者 30 天留存（有多少人提交第二次）。剔除率过低（0%）说明规则没在执行，过高（> 30%）说明门槛设计有问题。

## 6. Agent Olympics 黑客松

### 6.1 一句话赛题

> **设计你的交接协议，在给定任务上把 cost per success 做到最低，同时成功率不能低于 90%。**

不设「谁的任务更难」这类模糊目标，只比一个数，且这个数的定义在 spec 里写死。

### 6.2 赛制与评分

| 项 | 规则 |
|---|---|
| 参赛方式 | 个人或最多 3 人队；实现必须是公开仓库 |
| 提交物 | 一个 `MessageDesign` 实现（对应 `spec/MSG-DESIGN-SPEC.md` 的接口：`encode` / `decode` / `permittedActions`） |
| 硬性门槛 | 成功率 ≥ 90%；必须通过信息等价闸门（每臂 `renderToProse()` 的字段覆盖断言必须通过）；必须通过 `make verify` 的 10 个场景 |
| 排名 | 先过硬性门槛，再按 **CCI-C** 升序排名（见 5.2 的说明，主榜用 CCI-C 是因为它不含构造性零） |
| 并列处理 | CCI-C 相差 < 1% 时并列，并列者各得一份并列奖，**不做小数点后的人工裁决** |
| 公开性 | 所有提交在结果公布时全部公开源码与 transcript |

硬性门槛的两条是防止比赛变成「刷分游戏」：成功率门槛堵住「啥也不做」，信息等价闸门堵住「多说点话」。这两条与论文的公平性闸门完全一致，**参赛者跑的是与论文同一套闸门**，这是赛事公信力的全部来源。

### 6.3 时间线

| 阶段 | 时间 | 产出 |
|---|---|---|
| 报名与赛题发布 | 2027-06-01 至 06-14 | 赛题、锚点套件版本、样例实现 |
| 开发期 | 2027-06-15 至 07-15（31 天） | 每周一次公开 leaderboard 快照，鼓励早交 |
| 提交截止 | 2027-07-16 | 提交 PR |
| CI 重测窗口 | 07-17 至 07-25 | 维护者重测全部提交 |
| 结果公布 | 2027-07-27 | 全榜、源码、转写脚本、博客 |
| 复盘 workshop | 与 CIST 或 ICIS 同期 | 30 分钟，录屏公开 |

### 6.4 奖品

| 名次 | 奖品 | 附加 |
|---|---|---|
| 第 1 名 | 2000 美元等值（GitHub Sponsors credits 或 API credits）+ 论文附录署名致谢 + 排行榜永久标记 | 不要只给钱，给署名 |
| 第 2、3 名 | 各 500 美元等值 + 排行榜标记 | 无 |
| 并列奖 | 5 名，各 100 美元等值 | 应对 CCI-C < 1% 的密集并列 |
| 最佳新协议 | 500 美元等值，评的是「与 F/S/C 都不同的协议设计」而非名次 | 鼓励真正的创新而不是微调 |
| 参与奖 | 全部合格提交的作者进 `leaderboard/hall-of-fame.md` | 参与本身即奖励 |

**奖品结构的关键**：第 1 名给论文致谢与永久标记，而不是只给钱。对参赛的工程师和研究者而言，被一篇预印本致谢的长期价值高于几千美元，这一条能把参赛质量拉高一档。

### 6.5 参赛者从哪来

| 来源 | 怎么把人带进来 | 预期人数 |
|---|---|---|
| Agent 框架社区 | 在 LangGraph / AutoGen / CrewAI 的 Discord 与 Discussions 发赛题；给三个适配器的维护者发定向邀请 | 8 到 12 队 |
| HN / Reddit 定向帖 | 只发一次，附「我们的门槛和我们自己的分数」，不放空谈（见第 8 节） | 3 到 5 队 |
| 高校 | 给做 AI 协作 / 多智能体的实验室发邮件（模板附 5 分钟上手） | 2 到 4 队 |
| 论文读者 | 预印本引用页与 GitHub README 的显著入口 | 2 到 3 队 |

合计预期 **15 到 24 队**。低于 10 队就降级为一次「榜单刷新活动」，不硬撑成赛事并在对外材料里如实说明规模。

## 7. 发布节奏

### 7.1 三条独立的版本线

一个仓库里有三个会各自演进的东西，必须分开版本号，否则读者无法判断「升级到 0.4.0 会不会让我的 CCI 分数失效」。

| 版本线 | 格式 | 何时改 | 兼容承诺 |
|---|---|---|---|
| **库**（`handoffpack` npm 包） | semver `MAJOR.MINOR.PATCH` | `src/` 行为变化 | MAJOR 改 API 契约，MINOR 加功能，PATCH 修 bug |
| **锚点套件**（benchmark） | `cci-anchor-v1` | 任务、种子、ground truth、模型快照任一变化 | **新版本号，不原地改**。旧版本永远可复现 |
| **提交格式**（榜单） | `submission-v1` | `submission.json` 字段变化 | 加字段是 MINOR，删改字段是 MAJOR |

**0.x 规则**：在 `make verify` 连续 10 次绿、`src/` 的公共接口冻结、且至少被一个外部仓库依赖之前，库保持 `0.x`。**这三件事同时满足才发 `1.0.0`**，不做「感觉成熟了就 1.0」。

### 7.2 CHANGELOG 规则

格式：**Keep a Changelog**（`CHANGELOG.md`，按 `Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security` 分组）。

六条硬规则：

1. 每个条目以 `PR #编号` 结尾，可追溯。
2. 每条条目必须能被一个用户验证：「运行 X 会看到 Y」。「改进了性能」这种句子不许写。
3. **测量定义的变化单列一节 `Measurement Changes`**，格式是「指标 M：旧值定义 → 新值定义，差多少（用一个具体数字说明）」。这是本项目独有的、最重要的一节：CCI 分数会因测量定义变化而不可比，必须在变更发生的那一周就说清楚。
4. MAJOR 版本在 CHANGELOG 顶部附迁移指南。
5. 破坏性变更在 release notes 顶部加一行加粗警告。
6. 每周五随 release 一起发布，不攒。

### 7.3 节奏表

**每周**

| 日 | 动作 |
|---|---|
| 周一 | 上周 issue 与 PR 清理；确认本周 release 的内容范围 |
| 周二至周四 | 开发与评审；Demo Day 内部演示（每周五 30 分钟，每人 demo 一个能跑的东西） |
| 周五 | 发 release + CHANGELOG 更新 + 一条社区可见的进展（GitHub Release 说明或讨论帖） |

**每月**

| 动作 | 说明 |
|---|---|
| 榜单刷新与 anchor 健康检查 | 提交数、被剔除率、重测完成度 |
| 规范复核 | `spec/` 三份文档与 `src/` 实现是否仍一致，差异要显式记录 |
| 一条社区内容 | 博客或技术帖，题目必须来自真实被问到的问题 |
| 成本账本对账 | 实验花的美元，与 `--max-spend` 闸门比对，超支要写原因 |

**每季**

| 动作 | 说明 |
|---|---|
| 模型漂移探针 | 固定 20 个种子用当时的 frontier 模型重跑 T3，报告结论漂移幅度。这是本项目长期信誉的基石 |
| 依赖审计 | 六个本地技能按 Snyk 2026-09 的审计口径复查；依赖有 CVE 就在一周内发 patch 版本 |
| 路线图复盘 | 哪些里程碑没打勾，为什么 |

**关键纪律**：**周节奏不断。** 断更一次，之后再想恢复「每周一个 release」的读者预期，成本是之前的三倍。宁可某周只发一个 PATCH 只修 typo，也不断更。

## 8. 分发的克制判断

增长最常见的失败方式不是做得少，是**到处都发**。下面这张表是明确的不做清单与做清单，理由比清单本身重要。

| 渠道 | 判断 | 理由 |
|---|---|---|
| **Hacker News** | **做，但有硬条件** | HN 的规则是「Show HN 要可运行」。**必须有一条别人能在自己机器上一行跑起来的命令，且这条命令 60 秒内出可见结果**。发「我们写了一篇论文」在 HN 是零转化；发 `npx handoffpack bench --demo` 加真实数字表，才有讨论。HN 用户会自己跑，跑不通就再也没有第二次 |
| **Reddit**（r/LocalLLaMA、r/AI_Agents、r/MachineLearning） | **做，但有硬条件** | **每个 subreddit 的实际规则不同，部分禁止纯项目宣传**。发之前逐个读该版的规则栏。可行的做法是发「我们测了三种交接协议，结果如下（完整数据表）」这种**数据帖**，把项目放在末尾一行链接。数据帖在 r/LocalLLaMA 是受欢迎的形态，纯宣传帖会被删 |
| **X / LinkedIn** | **做，低投入** | 这两个渠道的算法只奖励「有具体数字的短帖」。每天 15 分钟，发自己的数据，不发行业观点。**不要指望它带来 star，只指望它带来 10 到 20 个学术传播的种子** |
| **YouTube / Bilibili 教程** | **做，投入 1 天** | 4 分钟录屏，标题写「多智能体流水线 token 成本实测」。视频的搜索长尾能持续两年，是少数投入产出比长期为正的渠道 |
| **知乎 / 公众号** | **做，中文语境必做** | 本项目的主要作者与潜在读者群在中文语境。一篇「我们如何定义智能体的协同成本」的中文长文，比三篇英文博客在中文圈传播更远 |
| **技术博客（Dev.to / Medium）** | **做** | 目标是搜索长尾与学术人群，两周一篇。题目必须来自真实被问到的问题 |
| **Product Hunt** | **不做** | Product Hunt 的用户是独立开发者与工具选型者，本项目的读者是工程师与研究者，**人群错配**。而且 PH 需要「第 5 名产品」的日常运营，对一个季度发布一次的项目是纯损耗 |
| **广告投放** | **不做** | 无预算约束的投放对一个学术开源项目是纯浪费。项目的转化路径是「搜索 → 看 README → 跑 → star」，投放打断的是这个路径而不是缩短它 |
| **批量给不相关仓库提 PR** | **不做，明确禁止** | 会永久损害仓库信誉，且被 PR 的人一眼看出。宁可只给真正用了本项目的仓库提 PR |
| **赞助 / 付费 newsletter** | **不做** | 与本项目的收入结构无关。工件与榜单的复利来自引用与标准地位，不来自订阅 |
| **自己的 Discord 服务器** | **不做（早期）** | 少于 500 名活跃成员前，Discord 是纯维护负担。把这个预算换成「在别人已有的社区里持续输出高质量回答」更划算 |

**一条贯穿所有渠道的原则**：**任何一次分发都必须附可复现的一行命令或一张真实数据表。** 这不是形式主义，是这个项目唯一与营销型开源项目不同的地方。我们的差异化就是「敢把不利于自己的数字一起放出来」（`C` 臂比 `F` 臂贵），这个姿态必须一以贯之，否则整套打法失效。

## 9. 风险：什么会让增长失败

按「一旦发生就无法补救」的程度排序。

### 9.1 致命级

| 风险 | 早期信号 | 缓解 |
|---|---|---|
| **论文没中** | 2027-06 的 CIST 决定 | 预印本与榜单的路线**不依赖论文中**。榜单本身可以独立活，因为它测的是协议不是论文。**不要把增长计划全部押在论文上**，这是本文件最重要的一条 |
| **论文中了但主张被削弱** | R1 审稿意见要求缩小到「agent 特有，不外推到人类组织」 | 这几乎必然发生，且已经在 `docs/04-论文计划.md` 第 6 节 A5 里预判。主张缩小不影响榜单与工具的可信度，只影响一句话的野心 |
| **arXiv 预印本与 IS 双盲冲突** | 见 `docs/04-论文计划.md` 第 7 节冲突 4 | 2026-12 前决策，默认选项 1 |
| **模型漂移让主结论失效** | 漂移探针显示某条假设的效应量掉到 0 附近 | 漂移探针每季跑一次，**结果无论好坏都公开发布**。这既是诚信也是护城河：只有公开漂移数据的项目才敢被依赖 |

### 9.2 严重级

| 风险 | 早期信号 | 缓解 |
|---|---|---|
| **榜单被刷** | 剔除率异常（> 30% 或 < 2%）、提交数突然集中在一周内 | CI 重测是唯一防线。若仍被攻破，公开剔除记录并公布攻击手法，让攻击者失去隐蔽性 |
| **CCI 的构造性零问题** | 有人指出 `C_adapt` 在 `C` 臂上恒为零 | 主榜已改用 CCI-C 避开该成分；CCI-Adapt 只作诊断列，且只在 `C-shadow` 上有解释力。榜单页公开三种 CCI 的并列显示与差异说明。规范见 `spec/COORDINATION-COST-SPEC.md` |
| **周发布节奏断掉** | 连续两周没有 release | 「宁可只发一个 PATCH 修 typo 也不断更」这条纪律写进第 7.3 节，就是为这个风险 |
| **贡献者流失** | 连续三周只有一个人提交 | `docs/06-分工与里程碑.md` 的 Demo Day 与「一步一退出条件」的切分就是为了让第二个人随时能接手 |

### 9.3 值得担心但不致命

| 风险 | 说明 | 缓解 |
|---|---|---|
| **被大厂同类项目挤出** | 某个 agent 框架厂商发布自己的 handoff 规范并占据心智 | 护城河是**公开基准与预注册**，不是规范本身。规范可以被抄，基准的时间戳不能伪造 |
| **工程精力被论文吃掉** | 榜单与适配器全部延期 | 榜单在 P4 结束后排期，第 4 节的排序表已经把它放在论文之后但**不晚于 2027-03**。这条是硬边界 |
| **模型 API 涨价或限流** | 主网格跑不完 | `--max-spend` 闸门已设计为硬停；可复现子集用开源权重模型作为兜底 |
| **过度增长压垮维护** | issue 与 PR 数量超过每周可处理量 | **接受排队，并把排队状态公开在 README 上**。一个明确写着「PR 响应时间约两周」的仓库，转化率高于一个假装很快的仓库 |

## 10. 一页纸执行摘要

| 什么时候 | 做什么 | 判定 |
|---|---|---|
| 2026-11 起 | 每周五一个 release + CHANGELOG | 连续 12 周不断更 |
| 2026-12 | 定 arXiv 与 IS 双盲的冲突解法；确认 CIST/ICIS 政策 | 决策记录写进 `docs/04-论文计划.md` |
| 2027-02-20 | 数字冻结 | `numbers_manifest.json` 无占位符 |
| 2027-02-26 | arXiv 上线 | 徽章、BibTeX、CITATION.cff 全部就位 |
| 2027-02-27 | HN 首发 | ≥ 100 points，带一行可跑命令 |
| 2027-03 | 榜单上线 + 演示视频 + 博客 | 月活访问 ≥ 200 |

**一句话默认建议**：先把尺子造准（论文与基准），再让人看见（README 首图 + 一行命令），最后才让人参与（榜单与黑客松）。顺序反了，每一步的转化率都会掉一半以上。
