# 02 实验设计

> 一句话故事：本文用 agent 仿真组织协作，对照自由文本（F）、结构化（S）、结构化+契约（C）三种交接消息设计，度量它们对**协同成本四个成分**（搜索解析 / 表达转述 / 事中协调 / 事后适应）的影响，并通过预注册锁定假设，通过任务族与拓扑的网格覆盖单一论文最常被击穿的“模型特定”威胁。

## 2.1 研究问题与假设

### 2.1.1 核心研究问题

RQ1：交接消息设计在 F / S / C 三个层级之间移动时，协同成本的哪个成分下降，下降多少，是否在大规模组织中保持。
RQ2：效果是否随任务不确定性、组织拓扑与组织规模变化，哪一种交互是显性的。
RQ3：以「每次成功任务的成本」（cost per success）衡量，S / C 是否真的优于 F，还是只是把同一笔成本挪到不同会计科目里。

### 2.1.2 假设矩阵

H1–H5 与 `00-总体规划.md` 的表述一致。下表给出每个假设的**操纵变量**、**结果变量**、**控制变量**与**预期方向**，写实到可以直接进入预注册表。

| 假设 | 操纵变量（自变量） | 主结果变量 | 次结果变量 | 控制变量 | 预期方向 | 效应机制 |
|---|---|---|---|---|---|---|
| **H1** | 设计（D）：F → S | C_search, C_spec | clarification_rounds, first_pass_comprehension, redundant_constraint_rate | 模型、topology、N、task instance seed | C_search ↓, C_spec ↓（receiver 侧更强） | 远距离知识必须显式编码，结构化消除“猜测字段含义”的成本 |
| **H2** | 设计（D）：**S → C-shadow**（不是 S → C） | C_adapt | verify_failures, out_of_scope_actions, rework_rounds, **c_would_block** | 同 H1 | C_adapt ↓；S 与 C-shadow 在 rework_rounds 上差显著 | 声明义务本身就是信号，不靠强制也能减少事后返工。**强制那一层只报拦截计数（`c_would_block` 对 `c_blocked_by_enforcement`），不报适应成本效应** |
| **H3** | 设计（D）× 任务不确定性（U） | C_adapt（S vs C-shadow 的差） | cost_per_success（S vs C-shadow） | 模型、topology、N | 在高 U 任务上承诺的边际收益为正且最大；在低 U 任务上可能为负（过度契约） | 契约有固定签发与验签开销，低争议任务上签发成本吞噬收益 |
| **H4** | 设计（D） | C_spec 上游 | cost_per_success（每个成分分开报） | 同 H1 | C 的 sender_tokens ↑，但 cost_per_success 仍 ↓ 或持平 | 成本转移而非消失：把下游猜的成本变成上游写的成本，总成本下降 |
| **H5** | 设计（D）× 组织规模 N（8/32/96） | cost_per_success（S vs F） | cost_per_success | topology 固定为 chain（最易识别规模效应） | log-log 模型 `log(cost) ~ log(N) + D + D:log(N)` 中 **`β(D:log N) < 0`**，即结构化臂的成本随 N 增长更慢，节省随规模扩大 | 信息在长链路中衰减，结构化把衰减变成可重读的字段，让动作无法绕过 |

**机制注释（审稿人挑战 H1 / H2 的第一刀）**

- H1 不是“结构化赢在写得更多”：所有“信息”三臂是同一份 pack（见 2.2.3 公平性闸门）。
- H2 不是“结构化赢在强制执行”：C 与 S 的字段几乎一样，C 只多一份 capability token 把违规改成签名失败。同一个发件人能在 S 写出“禁止修改 X”，但只有 C 能强制它。
- H3 用任务族内嵌的“争议度量”量化低 U vs 高 U，避免主观调档。
- H4 把 sender vs receiver 拆开报，否则“成本转移”会被总成本均值的统计掩盖。
- H5 的超线性用 Δlog(C) 与 Δlog(N) 的弹性估计，不是单点斜率。

### 2.1.3 调节变量与未列入主假设的次要变量

- **任务不确定性（U）**：任务的解是否唯一、是否存在多种合法 final answer。T0 低，T1 中，T2 中，T3 高。用作 H3 的调节变量，编码与 `docs/03-分析与统计计划.md` 第 3.7.3 节一致。
- **组织拓扑（T）**：chain / tree / hub-and-spoke / mesh。见 2.4。
- **组织规模（N）**：8 / 32 / 96 agents，在 chain 上可补测到 128（预注册允许扩展，但默认 96）。**四种拓扑的 id 固定为 `chain` / `tree` / `hub-and-spoke` / `mesh`，不设第五种。** 见 2.4.5。

## 2.2 三臂的精确操作化

### 2.2.1 唯一差异轴

三臂的差异不在“写得多少”，而在**接收方义务的执行点**：F 是隐性、S 是显式声明、C 是声明且被签名强制。这一点是 H1 / H2 是否能成立的前提。`spec/MSG-DESIGN-SPEC.md` 已统一术语，本节只给出实验侧的执行细节。

### 2.2.2 三臂的载体与字段清单

| 臂 | 载体 | 字段（接收方可见） | 边界执行点 | token 模型 |
|---|---|---|---|---|
| **F** 自由文本 | 一段散文，由 `renderToProse(pack)` 机械生成 | 全部以散文形式呈现；无字段 | 由模型合规 | 无 |
| **S** 结构化 | JSON pack，zod 校验通过 | `situation, background, assessment, recommendation, scope.actions, scope.context_refs, deadline, verify`（prose string） | 接收方按声明理解 | 无 |
| **C** 结构化 + 契约 | `S` 的全部 + capability token | 同 S + `token { jti, scope, issued_at, expires_at, parent_handle, sig }` | token 验签在每次调用前发生 | 链式 HMAC（macaroon 风格）+ `jti` 单次使用 |

**为什么 C 比 S 多 token 而不是多规范**：token 不是规范。是把“禁止”从模型必须遵守改成“签名失败时调用方也无法动手”。同一个收件人在 S 模式下越界调用会成功，在 C 模式下会因签名失败立即拒绝，调用方收到 401 而不是 “违反 policy”。这是 H2 的机制来源。

### 2.2.3 公平性闸门（审稿人第一刀）

**法则**。同一份 pack `p` 的三臂携带完全相同的信息：

- `F(p) = renderToProse(p)`
- `S(p) = p`（JSON）
- `C(p) = p ⊕ token(p)`，其中 `token(p)` 是 `p` 的确定性函数。

**为什么必须是机械降级而非 LLM 改写**。如果 `F` 交由 LLM 重写散文，F 臂会变成“写作质量”比赛而不是“消息设计”比赛：写得越生动越像“free text 赢了”。这种伪信号会污染整篇论文。机械降级把“质量”维度钉死在版式上，把可变性挤回“是否给字段”这一个开关。

**`renderToProse(p)` 的机械模板**（已在 `MSG-DESIGN-SPEC.md` 中定义，实验侧复述）。它必须：

1. 是纯函数，无 LLM 调用
2. 字段拼接模板固定，列表用逗号 join
3. 输出 ASCII 行，禁 emoji、禁破折号、禁可变时长叙述

```
handoff {to.agent} in {to.workspace}:

situation: {p.situation}
background: {p.background}
assessment: {p.assessment}
recommendation: {p.recommendation}

you may perform: {p.scope.actions joined ", "}
context you may reference: {p.scope.context_refs joined ", "} (resolve with your own permissions)
this expires at {p.expires_at}
the sender will check the result with: {p.verify.statement}
```

**`verify` 双渲染：statement + predicate**。`verify` 在创建时拆成两个字段：

| 子字段 | 形式 | 哪些臂带 | 用途 |
|---|---|---|---|
| `verify.statement` | 一句规范化人类可读的句子，由 predicate 确定性地生成，禁止手写旁注 | F、S、C 都带 | 三臂的接收方看到的同一句可读合约 |
| `verify.predicate` | 机器可判的 `{ kind, args }`，注册到 checker 字典 | 仅 C 带 | C 臂 `close` 时由 checker 执行 |

**为什么不允许"F 单独脱敏 verify"**。在三臂不一致的 verify 文风下，F 等于被赋予了“特殊提示词”，正是 AGENTS.md 规则 12 与本节公平性闸门从根反对的事。正确做法是在源头保证 `verify.statement` 可由 `verify.predicate` 唯一复原、且 C 单独持有 predicate；F 不被特殊照顾，也就不被污染。

**公平性验证（必跑）**。每个 run 在归档时强制 audit 三件事，audit 失败者**丢弃，不修补**：

1. **字节数差异**：报告 `|bytes(F) − bytes(S)|`、`|bytes(F) − bytes(C)|`，理由：S 与 F 通常接近（散文 vs JSON），C 因带 token 一定 > S，但 S 与 F 的相对大小不应差异过大；若 `bytes(F) ≫ bytes(S)`，提示 `renderToProse` 写出无意义前缀，必须停跑。
2. **token 数对照**：用统一的 tokenizer（默认 `o200k_base`）对每个臂作为字符串编码后取 token 数，报告 `tokens(F) / tokens(S)` 与 `tokens(C) / tokens(S)`。预期 `tokens(C)/tokens(S) ≤ 1.4`，超过即 token 设计问题。
3. **字段覆盖断言**：写一个 grader，断言模板 `renderToProse(p)` 的输出包含 `p` 中每一个字段的非空值，**并断言 `verify.statement` 能由 `verify.predicate` 通过同一渲染函数复原**（同一函数对同一 predicate 每次输出同一句子）；任一断言失败，run 失败（这是 writing bug，不是数据 bug）。

**F 臂的人类范例（仅作 prompt priming，不作 F 臂生产路径）**。在 system prompt 注入 3 个人类撰写的优秀范例（手动写一次，三臂均注入），让三臂的接收方看到同样的阅读期望；如果不注入，只在三臂不等量提示词下测 F，结论不公平。

### 2.2.4 三臂的模型能力下限与上限

| 臂 | 强制要求 | 信任假设 |
|---|---|---|
| F | 接收方能从散文提取字段；调澄清轮的代价构成 C_search | “人是听话的”这个假设不可避免，否则臂无法成立 |
| S | 接收方按 JSON 字段读取；调 zod schema | schema 不可绕过；JSON 不被改字段名 |
| C | 同 S + 接收方每次调用前验签 + token 服务拒绝重放与跨 scope 调用 | token 服务可用，且签名链真实（P0 必修：当前 `narrowToken` 是 P1 第一刀） |

## 2.4 操纵变量 2：组织拓扑（T）

四种拓扑，每种描述节点、边的方向、交接发生条件。本节用 ASCII 图给出交接语义。

### 2.4.1 Chain（链）

适用组织：装配线、流水线、串行决策链。每个节点只有一个上游、一个下游（除首尾），交接严格线性。

```
   [n0] -> [n1] -> [n2] -> [n3] -> ... -> [nN-1]
```

交接语义：每个非尾节点发出恰好 1 个 pack 给唯一后继；尾节点将完成结果回传首个节点或汇总池。N=96 时最长路径 95 跳。

**为什么测**：超线性规模效应（H5）在链上最易暴露：信息衰减随跳数单调累加。

### 2.4.2 Tree（树）

适用组织：层级管理、瀑布式需求分解。每个节点可有多个子节点，一个父节点（除根）；一个非叶节点向每个子节点发一份子 pack。

```
            [root]
           /  |  \
        [c1] [c2] [c3]
       / | \       |
    [..][..][..] [..]
```

交接语义：根节点发 N_children 个 pack 给直接下属；叶节点结果向上聚合到父节点；父对子合并后向根汇报。交接总次数 ~2N（每边算一次）。

**为什么测**：与 chain 比，可看到下游 fan-out 时的冲突解决成本（同一父对多个子发出冲突 verify 时，子节点如何汇报）。

### 2.4.3 Hub-and-spoke（中心辐射）

适用组织：协调者 + 专家池。中央 hub 接收所有 spoke 反馈并再分发；spoke 节点不直接通信。

```
        [s0]  [s1]  [s2]  [s3]
           \   |   /  \   |  /
             [ hub ]
           /   |   \  /   |  \
        [s4]  [s5]  [s6]  [s7]
```

交接语义：spoke 与 hub 双向通信；spoke 之间通信必须经过 hub 中转（hub 可附 token 转发）。hub 是 single point of coordination。N=96 时 hub 入口流量是 O(N)。

**为什么测**：暴露 hub 拥塞与 read-time cost（C_search 在 hub 集中积累），与 chain 的逐步衰减形成对比。

### 2.4.4 Mesh（全连接）

适用组织：网状协同、自组织团队。每对节点都可通信，每对节点都可发包。

```
     [s0] - [s1] - [s2]
      |  \  |  X  |  /
     [s3] - [s4] - [s5]
      |  /  |  X  |  \
     [s6] - [s7] - [s8]
```

交接语义：每对节点可发 pack；接入图由 Erdős-Rényi 邻接率 `p_edge` 控制，不预设 k 跳上限。**`p_edge` 是预注册参数**：

| `p_edge` | 角色 | 单元格 |
|---|---|---|
| 0.25 | **主分析默认** | mesh 主网格所有 cell |
| 0.10 | **稳健性 / ablation** | mesh 在 chain 主分析对应的 N 集合上重跑一版 |

主分析固定 `p_edge = 0.25`，0.10 是审稿人若要求“mesh 也呈完整 H5”时的预备方案，而不是 rebuttal 临时补的（此预备方案列入预注册，不在注册后另启）。

交接总次数上界 O(p_edge · N²)；N=96、p_edge=0.25 时为 2280 次调用上限，预算护栏触发降采样与降 R（见 2.13）。N=96、p_edge=0.10 时仅 9 个 cell 调 R=10，其余 mesh cell 走主网格默认 R。

**为什么测**：N↑ 时结构性差异（结构化能否挽救 quadratic 退化）。

### 2.4.5 规模 N 的取值与“几百个 agent”锚点

三个固定水平 **N ∈ {8, 32, 96}**，主网格 R=20 seeds。同时保留 **N=128** 作为可扩展点（仅在 chain 上做补测）。

为何 N=96 是“几百”落点：与 OC-P1 的可比范围对齐（OC-P1 多 LLM 节点上限约 80）；与 HICSS 2025 类市场均衡仿真的节点数同量级；chain 上 95 跳足以让消息内容衰减可见。

| N | chain 跳数 | tree 深度（4 叉） | hub-and-spoke spoke 数 | mesh 边数（k=0.25） |
|---|---|---|---|---|
| 8 | 7 | 2 | 7 | 16 |
| 32 | 31 | 3 | 31 | 248 |
| 96 | 95 | 4 | 95 | 2280 |

## 2.6 任务族 T0 / T1 / T2 / T3

四族任务各有 ground truth，可独立完成主成分测量。

### 2.6.1 T0 玩具冒烟（CI only）

- **任务描述**：3–5 跳串行交接，每跳验证“上一跳发出的字段是否被正确解析”。无内容真实性要求，只测字段解析与重新打包。
- **agent 角色**：唯一角色是“echo-and-forward”，无领域知识。
- **ground truth**：字段完全相等为 1，否则 0。
- **测出的成本成分**：`C_search` 与 `C_spec` 中性测量（剥离任务复杂度），用作 sanity check 与 C0 sanity baseline。
- **生态效度**：低。作为冒烟与 CI 用，不进入主网格。

### 2.6.2 T1 博弈收敛（解析最优解）

- **任务描述**：N 个对称定价 agent（`chain` / `tree` / `hub-and-spoke` 中一个被指定为“定价代理”，其余节点选价）需要在 R 轮内互相协调收敛到某对称纳什均衡 / 串谋均衡 / 一价均衡，由任务族调度。
- **agent 角色**：每个 agent 是一个“报价者”，持有私有成本；接受邻居报价，决定自己下一轮报价。
- **ground truth**：博弈的解析最优解（计算得到，或查表），度量 |report_price − optimal_price| 的相对距离。
- **测出的成本成分**：`C_coord`（消息往返数）、`C_spec`（每条报价的 token）、`Q`（最优距离）。
- **为什么这个任务测出 C_coord**：博弈本质是消息往返；结构化对往返数的影响是直接的。

### 2.6.3 T2 软件交付流水线（单元测试 ground truth）

- **任务描述**：N 个 agent 模拟一个微型研发团队：PM 发需求 → 架构拆分 → 实现 → 测试 → review。任务实例是一段 5 文件 / 100–300 行的 npm 包。每个 agent 角色：PM / 架构 / 实现 / QA / review。
- **agent 角色**：5 个固定角色，N 包含冗余（实现可被复制 2–8 个并行）。
- **ground truth**：单元测试集 + 静态检查（lint）通过率，每个 run 自带一份 gold unit test（任务实例种子化生成）。
- **测出的成本成分**：`C_search`（实现者猜需求），`C_adapt`（verify_failures，因 verify 可编译为“通过 lint + 通过 unit test”）。
- **为什么这个任务测出 C_adapt**：verify 是机器可执行的，H2 直接落在这里。

### 2.6.4 T3 长文档研究简报（rubric + LLM-judge）

- **任务描述**：N 个 agent 模拟一个研究小组：3 个研究员 / 1 个整合者 / 1 个审稿。任务实例是一段 200–500 词论文摘要 + 数据表，每位研究员从不同角度写 1 小节，整合者合并。
- **agent 角色**：固定。
- **ground truth**：rubric-based 评分（10 条维度，每条 0–5 分），LLM-judge 同 prompt 由前沿模型评；**人类校准子样本**：每个任务实例从 runs 中采 5 条最差 + 5 条最好 + 5 条中位，由人类专家（研究者本人 + 1 个独立审稿）各自独立打分，计算两个一致性指标，**两条门槛分开判**：

  | 指标 | 算什么 | 不达标怎么办 |
  |---|---|---|
  | Spearman ρ | LLM-judge 分与人类分在同一条 run 上的秩相关 | `ρ < 0.6` → **重写 judge prompt 并重评全部**，论文正文报重写后的版本，附录同时报重写前的版本与前后差值 |
  | Krippendorff α | 两位人类专家之间的互评一致性 | `α < 0.67` → 人类标准本身不可靠，**T3 整族移入附录**，正文结论不得依赖 T3 |

  两条门槛各管一件事：ρ 低说明裁判不行，重写裁判能救；α 低说明真值不存在，重写裁判救不了，只能把这一族降级。早期的“ρ < 0.6 就重写”一条规则把第二件事混进了第一件事的处置里，等于用重写裁判去掩盖人类标准本身没有共识。
- **测出的成本成分**：所有四个成分，因为任务真实、跨人合作、需要合并返工。
- **生态效度**：高。这是现实知识工作任务的最小可计算近似。

## 2.7 因变量的操作化（每个成分的精确定义）

`spec/COORDINATION-COST-SPEC.md` 已定义信号。本节重写计算公式并加上实验侧采集点的版本号。所有信号每货币（tokens / USD / wall-clock seconds）单独报告；headline metric 用 USD，等价主图报 token，附录报 wall-clock（避免 timezone 与机器差异误导）。

### 2.7.1 C_search：搜索与解析

**定义**。接收方把发送方意图理解到“第一次动作是允许的”所需的代价。

| 子信号 | 公式 | 采集点 | 单位 |
|---|---|---|---|
| `clarification_rounds` | 在第一次正确动作前，接收方对发送方的“澄清型”turn 数 | transcript grader（关键词正则 + 模型共识） | 次 |
| `redundant_constraint_rate` | `\| 接收方重述约束 ∩ 发送方声明约束 \|` ÷ `\| 发送方声明约束 \|` | transcript grader | 比例 |
| `first_pass_comprehension` | 接收方第一次动作是否在 pack.scope 内（1/0） | token gate 或人工对照 S 臂 schema | 0/1 |
| `unresolved_fields` | `DecodeResult.unresolved.length` | `src/designs/decode.ts` return | 个 |

**总公式**

```
C_search = w1 * clarification_rounds(tokens)
        + w2 * redundant_constraint_rate
        + w3 * (1 - first_pass_comprehension)
        + w4 * unresolved_fields
```

权重在预注册内固定：`w1 = 1, w2 = 1, w3 = 2, w4 = 0.5`（H2 的机制不看 C_search，权重敏感度小）。

**货币换算**。`clarification_rounds` 用 sender_tokens + receiver_tokens 加权和；其他三个子信号用 USD 折算（`rate_provider(unit, model)`，同 `statsmodels` 的口径）。

### 2.7.2 C_spec：表达与转述

**定义**。上游写、下游读的代价。

| 子信号 | 公式 | 采集点 |
|---|---|---|
| `sender_tokens` | 包含 encode 调用的总 tokens | API usage |
| `receiver_tokens` | 包含 decode 调用的总 tokens | API usage |
| `payload_bytes` | carrier 字节数 | encoder |
| `message_count` | 完成单位工作所需的 handoff 数 | transcript |

**总公式**

```
C_spec = sender_tokens + receiver_tokens + payload_bytes(token-equivalent)
       + message_count * handoff_overhead
```

**关键拆解**。H4 的机制测的是 `sender_tokens(C) > sender_tokens(F)` 与 `receiver_tokens(C) ≤ receiver_tokens(F)` 的反差，必须分两侧报。

### 2.7.3 C_coord：事中协调

**定义**。交接本身发生的代价。

| 子信号 | 公式 | 采集点 |
|---|---|---|
| `handoff_latency_ms` | `t_receiver_first_action − t_sender_emit` | timestamps |
| `blocked_ms` | 接收方进入“等待上游结果”状态到“开始工作的状态切换”的时长 | dependency graph |
| `handoff_depth` | 完成 run 的最长 handoff 路径 | topology |

**总公式**

```
C_coord = handoff_latency_ms
        + blocked_ms
        + handoff_depth * depth_penalty
```

`depth_penalty` 默认 = sender_tokens of one hop，校准后定。

### 2.7.4 C_adapt：事后适应

**定义**。完成工作后为 handoff 后果买返工单的成本。

| 子信号 | 公式 | 采集点 | F | S | C-shadow | C |
|---|---|---|---|---|---|---|
| `verify_failures` | `verify` predicate 返回 false 的次数 | `verify` checker | ✓ | ✓ | ✓ | ✓ |
| `out_of_scope_actions` | 接收方调用未在 scope 的动作总数（含被拦的与未拦的） | token gate + model hook | ✓ | ✓ | ✓ | ✓ |
| `s_blocked_by_policy` | 上述越界动作中，由模型自律 / policy / 协议层面主动放弃的 | model policy hook | ✓ | ✓ | ✓ | ✓ |
| `c_would_block` | 观察模式下签名校验判定**应当拦截**的次数 | token gate | `null` | `null` | ✓ | `null` |
| `c_blocked_by_enforcement` | 上述越界动作中，由签名 / capability token **实际拦下**的次数 | token gate | `null` | `null` | `null` | ✓ |
| `rework_rounds` | 重做完成工作的次数 | transcript grader | ✓ | ✓ | ✓ | ✓ |
| `revoke_events`, `replay_blocks` | 撤销与重放拒绝事件 | `jti` ledger | `null` | `null` | ✓* | ✓ |

\* `revoke_events` 与 `replay_blocks` 走 `jti` 账本，与 scope 观察模式是两套机制，`C-shadow` 下照常生效。

**机制字段必须分开报**。`s_blocked_by_policy` 与 `c_blocked_by_enforcement` **不可相减**。原因：

1. F 与 S 臂根本没有 `c_blocked_by_enforcement` 的执行点，记为 `null`；记为 `0` 会让 MixedLM 的默认缺失值填补（均值）把它拉到与有意义的样本同列上，污染结构。
2. 即便在 C 臂内，两者度量对象不同：模型自律可能因 prompt 偏差更严，签名执行则更严；相减得到的差没有意义量纲。
3. 论文正文固定用法为 **“机制差异（C 独有执行点）”**，不是 **“C 比 S 在该字段上更低”**。相减叙事的反例是：`(out_of_scope_S − out_of_scope_C)` 没有机制意义，因为它把“模型是否拒绝”与“签名是否执行”混为一谈。

**`s_blocked_by_policy` 四臂全记，这是刻意的**。它度的是模型行为，而模型在四个臂里行为方式相同：它先被要求行动，再决定是否放弃，调用走到网关之前它已经有机会自律。执行顺序是“先生成、后网关”，所以强制不会截断模型自律的机会。只在 F 与 S 记，会把 `C-shadow` 唯一可观测的强制性邻近信号扔掉，而那恰恰是 H2 要用的臂。

**null 处理（前处理规则）**。MixedLM 入模前，两个执行点字段的结构性缺失如下，逐格列出，不写“共几格”这种会被后续改动算错的数字：

| 字段 \ 臂 | F | S | C-shadow | C |
|---|---|---|---|---|
| `s_blocked_by_policy` | 实数 | 实数 | 实数 | 实数 |
| `c_would_block` | `null` | `null` | 实数 | `null` |
| `c_blocked_by_enforcement` | `null` | `null` | `null` | 实数 |

- 结构性缺失一律禁止均值填补；只在该字段有值的臂上入模。
- `c_would_block`（观察模式）与 `c_blocked_by_enforcement`（强制模式）回答的是**同一个网关对同一批行为的同一个问题**，一个开着一个关着。把两者并排报，它们构成网关自身的**一致性校验**：若同一 `run_id` 下两数显著不等，说明网关在做规范之外的事，此时全部 C 臂结果存疑，先解释清楚再谈结论。

**总公式**

```
C_adapt = verify_failures * verify_cost
        + out_of_scope_actions * scope_cost
        + rework_rounds * rework_cost
        + revoke_events * revoke_cost
        + replay_blocks * replay_cost
```

公式中 `out_of_scope_actions` 是尝试总数，不区分被谁拦；机制证据来自子字段，不是该字段本身。

**机制字段报告原文（论文中写法）**

```
arm        |  out_of_scope_actions | s_blocked_by_policy | c_would_block | c_blocked_by_enforcement
F          |  8.4 ± ...            |  1.2 ± ...         |  n/a (no gate)   |  n/a (no enforcement point)
S          |  7.2 ± ...            |  6.8 ± ...         |  n/a (no gate)   |  n/a (no enforcement point)
C-shadow   |  7.9 ± ...            |  5.1 ± ...         |  6.4 ± ...       |  n/a (gate disarmed)
C          |  8.0 ± ...            |  0.4 ± ...         |  n/a (gate used) |  7.6 ± ...
```

要点一：`n/a` 有三种，含义各不相同，不可互换。`no gate` 是该臂没有网关执行点；`gate disarmed` 是网关在但不生效；`no enforcement point` 是设计上就无从执行。混写成一个 `n/a` 会让读者以为三者是同一件事。

要点二：`C-shadow` 的 `c_would_block` 与 `C` 的 `c_blocked_by_enforcement` 若来自同一批种子，应当接近。不接近就是网关实现有偏，全部 C 臂结论连带存疑。

要点三：这是机制差异报告，不是“分数排名”。

`verify_failures` 必须严格区分“真实 predicate 不通过” vs “verify checker 的实现 bug”。前者进 run，后者重跑；不在数字之列。

## 2.8 成本货币：tokens / USD / wall-clock

三种货币同时记录，互不替代：

- **tokens**：`o200k_base` tokenizer，统一口径；按 `sender_tokens + receiver_tokens` 报；不区 input vs output 因为模型定价不同，单独拆 input/output 在附录。
- **USD**：成本账本 `spend_ledger.jsonl`，每个 API call 写 `{ model, input_tokens, output_tokens, usd_at_call_time, rate_table_sha }`；分析时 `usd_at_call_time = input_tokens * input_rate + output_tokens * output_rate`，`rate_table` 冻结在 `bench/prereg/rates.json`。
- **wall-clock seconds**：每节点 wall-clock 时间，包含模型延迟与工具延迟；不包含 simpy 调度模拟的“虚拟”延迟。两者解耦。

**headline metric**：`cost_per_success = total_cost_usd / (n_runs * success_rate)`。三个货币都给，但 USD 为主。

**为什么用 USD 为主**。审稿人习惯读“钱”。token 会被“模型升级使 token 变便宜”干扰；wall-clock 会被机器性能干扰；USD 是“代价”的最直白代理，且经 rate_table 冻结避免回看。

## 2.9 随机化与种子控制

### 2.9.1 随机种子的来源、生成与归档

- **生成**：master seed 由 OS RNG 生成（`os.urandom(32).hex()`），写入 `bench/prereg/master_seed.txt`；实验启动时此文件被哈希进 `CONFIGS.sha256`，任何人改它即被 `verify_numbers.py` 抓到。
- **派生**：每个 cell（arm × task × topology × N）有 `cell_seed = SHA-256(master_seed || cell_descriptor)`；run seed = `cell_seed XOR run_index`。
- **归档**：每个原始 JSONL 行的第一条 metadata 包含 `master_seed, cell_seed, run_seed`，无 metadata 的行丢弃。
- **同种子重放**：bench runner 提供 `--seed <value>`，将覆盖派生，进入“同种子逐位复现”模式。承诺**字节级一致**：原始 JSONL 行哈希相同（除非模型 API 输出在 1 token 内漂移，这种情况记入偏差文件 `drift.jsonl`）。

### 2.9.2 随机化的层次

- **第一层（run 之间）**：cell 内随机化 task instance（同一 cell 不同 run 跑不同 seed 的同一任务谱）。
- **第二层（run 内）**：环境随机性（工具调用返回的环境 ID、并发执行顺序）；此层 simpy 提供确定性调度。

**为什么两层**：第一层让 cell 内方差有估计量；第二层防止“某 run 撞上特殊种子”造成伪信号。

### 2.9.3 复现性的护栏

1. 每条 API 调用 JSONL 落盘：`{ ts, prompt_hash, response_hash, model_id, stop_reason, usage }`。
2. `bench/prereg/rate_table.json` 与 `CONFIGS.sha256` 一同冻结；任何人离线重画图不应重算单价。
3. 约 5% 的 cell 用开源权重模型跑（仅 T0 / T1 / T2）；命名为 reproduce 子集，作 leaderboard 的 reference configuration。

### 2.11.2 冻结在哪里

**OSF**。`bench/prereg/` 目录包含：

### 2.11.3 `CONFIGS.sha256` 的作用与校验命令

**作用**。任何人想复现论文，应能跑：

```bash
sha256sum -c bench/prereg/CONFIGS.sha256
```

若任一文件被改，校验失败，跑出来的数字与预注册不一致。分析侧的 `verify_numbers.py` 会强制运行此校验。

**生成命令**。

```bash
cd bench/prereg
sha256sum protocol.md configs/*.json > CONFIGS.sha256
sha256sum substudy-cshadow.md > configs/substudy-cshadow.sha256
git add CONFIGS.sha256 configs/substudy-cshadow.sha256 && git commit -m "prereg: freeze configs <date>"
```

OSF 上传的是此版本。后续若改 `configs/`，SHA 自动变，必须显式修改 `CONFIGS.sha256` + OSF revision note。这是 P3 的退出条件之一。

### 2.11.4 Revision 通道纪律

OSF 上传的版本即“注册版本”。注册版本被默认为**冻结的、可对审稿人引用的语义**。后续任何偏离::R、p_edge、H 文本、子字段命名::一律走 OSF 官方 revision 通道，留下时间戳与 reason 字段。**禁止**静默替换、env-overridden 默认、隐式版本号、未注明的 fallback。任何 `verify_numbers.py` 不通过的痕迹都要在“Methods - Deviations from Preregistration”一节显式列出。

| 类目 | 触发条件 | 必需动作 |
|---|---|---|
| R 重设 | pilot 给出新功效 → 新 R | OSF revision + 论文 footnote |

| H 文本修订 | 中介分析反向鲁棒性触发 | OSF revision + 重新冻结 |
| 子字段增删 | `c_blocked_by_enforcement`、`c_would_block` 等 | OSF revision |
| 子研究扩格 | `C-shadow` 从 `T2`/两拓扑/`N∈{8,32}` 向外扩 | 子研究独立 OSF revision，**主网格 `CONFIGS.sha256` 不动** |

### 2.13.1 总预算估计（**占位值，待 pilot 校准**）

早期版本这里给了一个 `≈ 518,400 单位工作单元 → ~260k USD` 的粗算。**这个数作废**，两个毛病：它把 `R` 乘了两次（`R_avg=15` 之后又乘 `R=20`），并且把「一次组织级 run」与「一个 agent 的工作单元」当成同一个量纲。看起来精确的乘积掩盖了两个都没测的常数。

现在只冻结**可以数清楚的那一层**：

```
主网格 run 数（不含 T0 冒烟，不含人类基线，不含开源子集）:
  chain  T1,T2   : 3 arm × 2 task × 3 N     × R=20 = 360 runs
  chain  T3      : 3 arm ×        2 N       × R=20 = 120 runs
  tree,hub-and-spoke T2 : 3 arm × 2 topo × 2 N      × R=20 = 240 runs
  mesh   T1      : 3 arm ×        2 N       × R=10 =  60 runs
  mesh   T2      : 3 arm ×        1 N       × R=5  =  15 runs
  chain  N=128   : 3 arm × 2 task            × R=5  =  30 runs
                                              合计 ≈ 825 runs

C-shadow 子研究（2.13.4）:
  chain,hub-and-spoke T2 N∈{8,32} × R=20              =  80 runs
  对照行 S 复用主网格，不重跑
```

从 825 个 run 到美元，还差**两个必须实测的系数**：

| 缺的量 | 怎么得到 | 谁测 |
|---|---|---|
| 每个 run 的 agent 数（8 到 128 不等） | 从上表的 topology × N 逐格展开，是已知的，不是未知 | 静态计算 |
| **每个 agent-run 的 API 调用次数**（turn 数 × 每 turn 的重试） | **只能实测**。这是决定预算的那个数，目前完全是猜的 | P3 任务 3.2 校准 pilot |

所以现在能说的只有一句：**主网格约 825 个 run，子研究约 80 个 run，单价未知**。乘以校准 pilot 实测的「单 run 中位美元」才是预算，任务 3.3 由 Jason 确认上限。

任何在此之前出现的“主网格预计花费 $X”都不是本仓库的数字。

### 2.13.3 mesh 的 N≥32 限制与已知取舍

mesh（N = p_edge · N² 调用上界）在 N≥32、p_edge=0.25 时单 run 调用量二次增长；以 T1/T2 单价折算，远超其他 topology 的单 run 中位成本。因此行 16、17 把 mesh 的 R 显式降到 10 与 5。

**已知取舍**：

- 代价：H5 在 mesh 上功效受限。主网格 mesh 的 `power` 在 `d=0.3` 的探测阈值下不达 0.80。
- 不是事后调整：R 降与 N 集限制在注册时即如此（行 16 / 17 在 OSF 版本里相同）。
- 不是反驳时补救：若审稿人要求 mesh 也跑完整 H5，**预备方案**是 mesh 单独跑 `p_edge=0.10` 的 subgrid（N=8/32/96），该 subgrid 已**列入预注册**（见 2.11.1 第 11 项），不在 rebuttal 临时加。
- subgrid 仅扩展 mesh 上的 H5 显著性估计，不代替主分析。

**为什么 subgrid 必须保住 N=96，不能按二次增长的顾虑砍到 N≤32**。有人提过把 subgrid 限到 `N≤32`，理由是 mesh 的调用量随 N 二次增长。这条不采纳，理由是 subgrid 存在的全部意义就是覆盖主网格砍掉的那一端：

| 配置 | 单 run 调用上界 | 相对 p_edge=0.25 |
|---|---|---|
| mesh, `p_edge=0.25`, N=96 | `0.25 × 96² ≈ 2304` | 基准 |
| mesh, `p_edge=0.10`, N=96 | `0.10 × 96² ≈ 922` | **1/2.5** |

把 `p_edge` 降到 0.10 就是 subgrid 的省钱机制本身，它把二次项的系数除以 2.5。若再把 N 砍到 32，subgrid 的最远格子是 `0.10 × 32² ≈ 102`，比主网格 mesh 的 `N=32` 还便宜，但同时它也就**再也无法回答「结构化收益在最大规模上是否仍然成立」**。审稿人要求「mesh 上跑完整 H5」，要的正是 N=96 这一格；把它删掉，预备方案就变成了一个答非所问的空壳，而它仍然是写在预注册里的承诺。

代价照实说：subgrid 的 N=96 在 `p_edge=0.10` 下约为一个主网格 mesh cell 组的 1.8 倍调用量，不是零成本。若 pilot 数据显示它超预算，处理方式是走 OSF revision 缩小 N 上界并**在正文写明 subgrid 未覆盖 N=96**，不是悄悄不发那格。两者区别在于：前者是披露的取舍，后者是无法复现的缺口。

主网格默认 mesh 用 `p_edge=0.25`。该决定在 CONFIGS.sha256 的 configs/mesh.json 中固定。

### 2.13.4 `C-shadow` 机制子研究网格（**不属于主网格**）

| 行 | arm | task | topology | N | R | 备注 |
|---|---|---|---|---|---|---|
| S1 | S | T2 | chain, hub-and-spoke | 8/32 | 20 | 与 S2 共享任务实例与 seed，直接复用主网格的 `S` 臂 run |
| S2 | C-shadow | T2 | chain, hub-and-spoke | 8/32 | 20 | 网关 observe-only：验签、记 `c_would_block`、放行 |

对照行是 `S`，**不是 `C`**。理由在 `../spec/COORDINATION-COST-SPEC.md` 的 `C-shadow` 一节：强制生效时越界动作不会发生，`C_adapt` 按构造归零，拿 `C` 当对照等于用一个退化的格子去证明一个非退化格子好。

子研究只有 `T2` 一个任务族、两种拓扑、两个规模。`T2` 之所以够用：它是唯一同时具备**可执行 ground truth（单元测试）**与**真实事后适应（review 打回重做）**的任务族。`T0` 没有返工，`T1` 是单轮博弈无返工，`T3` 的返工由 judge 打分，成本归因会被 judge 自身的噪声吃掉。

**子研究独立预算行**：

```
C-shadow 子研究:
  - 格子 = 1 新增臂 × 1 task × 2 topo × 2 N = 4 格
      4 格 × R=20 seeds = 80 runs
  - 对照行 S 在主网格已有同 seed 同实例的 run，直接复用，不重跑
  - 单价同样未知，随主网格由 pilot 一起测
```

80 个 run 对主网格的 825 个 run，是 **9.7% 的额外 run 数**，别处取整写作「约 10%」。差别在于子研究只在 `N∈{8,32}` 跑，主网格的重量在 `N=96` 与 `N=128`。若按调用量而非 run 数计，比例更低，因为子研究最大的格子是 32-agent 的 hub-and-spoke。

**为什么不是四臂全网格**。四臂全网格会让每个 cell 多跑一个 run，而 `N=96` 的 mesh 与 `N=128` 的 chain 是最贵的两批格子，加一臂就要把它们全部重跑一遍，换来的信息只在 `C_adapt` 这一个成分上有用。子研究绕开这批格子，只在便宜的两拓扑两规模上保住 H2 可测。若子研究显示 `C-shadow` 与 `S` 无差异，那是真结果，照实报，不回头补四臂网格。

**子研究的读法**。它是机制诊断，不是第四个处理臂。主网格的三条假设各自的主对比不变：`H1` 用 `S` vs `F`，`H3` 与 `H5` 的交互项照旧在 F/S/C 上拟合。`C-shadow` 只回答一个问题：在什么都没拦的情况下，把义务写下来，返工会不会自己变少。
