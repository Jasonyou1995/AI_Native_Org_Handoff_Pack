# 01 · 工程计划

> 一句话故事：归档的 v1 计划里有 11 个已被证实的缺陷，其中两个不是 bug 而是论文机制缺失，所以 P1 先修签名链，再写三臂，最后才允许跑任何一次基准。

## 一、现状：这是一个没有源码的仓库

```
$ git ls-files | wc -l
17
$ ls -A src tests analysis leaderboard bench/tasks
analysis:
bench:
tasks
leaderboard:
src:
tests:
```

六个目录全部为空。仓库目前只有文档、许可证和治理文件，没有任何可执行代码。

这一点决定了本文的写法：**下面列的缺陷不是"代码里的 bug"，而是"归档计划里写错的代码"**。`archive/PLAN-v1-2026-10.md` 是一份 3682 行的逐步实现计划，它内嵌了 TypeScript 源码片段。缺陷存在于那些片段里。照着它实现，就会把这些缺陷一起实现出来。

因此 P1 的性质是"边实现边纠错"，不是"修一个已有系统"。每个缺陷都必须先在归档计划里定位到行号，再决定新代码怎么写。

## 二、缺陷分级

缺陷不是平铺的一张清单，是三层。三层的区别在于：**A 层不修，论文的核心论断无法成立**。

| 层 | 数量 | 性质 | 不修的后果 |
|---|---|---|---|
| **A 载荷层** | 2 | 论文的机制本身 | 假设 H2 没有中介变量，"结构 vs 承诺"退化成提示词差异，文章不成立 |
| **B 阻塞层** | 6 | 基准跑不起来或结果不可信 | 门禁是假的，数据不可复现 |
| **C 质量层** | 3 | 影响可用性与后续扩展 | 拖慢 P2/P3，不影响结论 |

> 说明：早期探索曾报"13 个缺陷"。本文只列**逐行核实过**的 11 条。没核实的传闻不写进必修清单，宁可少写，不可写错。

## 三、A 层：载荷缺陷（先修，其余全部等待）

### A1 · `narrowToken` 不验证父签名，且丢弃父链

**证据**：`archive/PLAN-v1-2026-10.md:1038-1043`（解析函数）与 `:1048-1063`（签发函数）。

```typescript
function parse(token: string): { scope: TokenScope; expires_at: string } {
  const [, payload] = token.split(".");
  return JSON.parse(fromB64Url(payload).toString("utf8")) as {...};
}

export function narrowToken(token: string, input: MintInput): string {
  const parent = parse(token);                       // 不验签
  ...
  return mintToken(input);                           // 用全局密钥重发，父链消失
}
```

**两个独立的问题**：

1. `parse()` 只做 base64 解码加 JSON 解析，**完全没有验签**。伪造的父 token 会被当成真父 token。
2. `narrowToken` 的最后一行是 `mintToken(input)`，它用**全局密钥**签发一张全新的 token，**没有把父 token 的摘要写进新 token**。结果是不存在真正的链式凭证（macaroon），任何人都能凭全局密钥造出任意一张 token。

**可观察症状**：写一个测试，把父 token 的签名部分改成乱码，其余保持不变，然后调用 `narrowToken`。v1 计划下这个调用会成功。

**为什么这是 A 层**：契约臂 `C` 的全部卖点是"越界调用在调用点失败"。但越界判断读的是 `token.scope`，而 `token.scope` 来自一张没有验签就能伪造的凭证。此时 `C` 无法报告任何强制拦截计数，假设 H2（承诺降低事后返工成本）失去中介变量，论文标题里的"承诺"就没有实体。

更直白地说：这种情况下 `C` 就是"戴了 token 的 `S`"。

**退出条件**：伪造父签名的调用必须抛错；新 token 必须携带父摘要且可逐级验证到根。

**顺序**：这是 P1 的**第一项**，排在写三臂之前。理由是三臂的 `C` 实现要调用 `narrowToken`，签名链没修好就先写 `C`，等于把错误实现固化成"实验仪器"。

### A2 · 自由文本臂缺少机械降级函数

**证据**：`archive/PLAN-v1-2026-10.md` 全篇没有 `renderToProse`（grep 结果为空）。

**问题**：三臂要公平，自由文本臂必须与结构化臂携带**完全相同的信息**，只是表现形式不同。如果自由文本是人工写的或模型生成的，那么 `F` 与 `S` 的差异就混杂了"写法质量"这个额外变量，测的就不是消息设计而是提示词工程。

**可观察症状**：`F` 臂的澄清轮次显著偏高，但这可能只是因为它少写了字段，而不是因为散文难以解析。审稿人第一刀就会砍在这里。

**退出条件**：`renderToProse(pack)` 是一个纯函数，任何人调用它都能得到 `F` 臂的字节；每次基准运行都输出字段覆盖审计（`pack` 的每个键是否出现在渲染后的散文中），审计失败的 run 直接丢弃而不是修补。

**已定的实现**：`spec/MSG-DESIGN-SPEC.md` 已写好该函数与模板，含 `verify` 的双渲染规则（`verify.statement` 散文给三臂，`verify.predicate` 机器谓词只给 `C`）。实现时以该 spec 为准，不重新设计。

## 四、B 层：阻塞缺陷

### B1 · `make test` 在容器里找不到测试文件

**证据**：`archive/PLAN-v1-2026-10.md:312-322`（Dockerfile `run` 阶段）、`:344`（compose 的 `target`）、`:260-261`（Makefile `test` 目标）。

Dockerfile 的 `run` 阶段只 `COPY` 了 `node_modules`、`package.json`、`src`、`demo`，**没有 `tests`**。compose 用的是 `target: run`。于是 `make test`（即 `docker compose run --rm app npm test`）在一个没有测试文件的容器里调用 vitest。

注意 Dockerfile 里另有一个 `test` 阶段（`:305-310`）确实 `COPY . .` 并包含测试，但没有任何东西使用它。

**退出条件**：`docker compose run --rm app npm test` 在干净环境里打印真实通过数。

### B2 · `make test` 与 `make verify` 跑的是同一条命令

**证据**：`archive/PLAN-v1-2026-10.md:131` 与 `:133`。

```json
"test":   "vitest run --reporter=default",
"attacks": "vitest run tests/attacks.test.ts --reporter=default",
"verify": "vitest run --reporter=default",
```

`test` 与 `verify` **逐字节相同**，而计划在 `:71-73` 声称 `test` 是"快速单元测试"、`verify` 是"全部 10 个场景"。计划后段 `:2279-2282` 修好了 `attacks`，但 `test` 与 `verify` 从头到尾没有分开过。

**为什么危险**：门禁是假的。全绿不代表 10 个验收场景跑过，只代表 vitest 没崩。`AGENTS.md` 要求三条命令真的不同。

**退出条件**：`test` 跑 `tests/unit/`，`verify` 跑 `tests/s01..s10`，`attacks` 跑 `tests/s08..s10`，三者的文件列表可从命令输出中区分。

### B3 · `package-lock.json` 从未被创建，但 Dockerfile 依赖它

**证据**：`archive/PLAN-v1-2026-10.md:302-303` 与 `:309`。

```dockerfile
COPY package.json package-lock.json* ./
RUN npm ci --omit=optional || npm install --omit=optional
```

`npm ci` 的语义是"严格按锁文件安装"，锁文件不存在时它直接失败。计划里的 `||` 兜底把失败吞掉了，于是问题被掩盖成"能装上"。同时 `AGENTS.md` 要求提交锁文件，但计划中**没有任何一个任务生成它**（全篇 grep 不到）。

**退出条件**：`package-lock.json` 提交入库；删掉 `|| npm install` 兜底后干净环境仍可 `npm ci`。

### B4 · `Store` 接口没有 `getRevoke`，逼出了私有字段强转

**证据**：`archive/PLAN-v1-2026-10.md:1201-1204`（接口）与 `:1291`（使用点）。

```typescript
export interface Store {
  revoke(handle: string, reason: string, at: Date): Promise<void>;
  isRevoked(handle: string): Promise<boolean>;
}

const entry = (store as MemoryStore)["revoked"]?.get(handle);   // 强转 + 索引私有字段
```

接口只能回答"是否已撤销"，不能回答"为什么撤销"。实现为了拿到 `reason`，绕过接口直接读 `MemoryStore` 的私有 Map。

**后果**：`Store` 的整个存在意义就是可替换实现，而这一行让任何非 `MemoryStore` 实现都拿不到撤销原因。换成 SQLite 实现时这里会静默返回 `reason: "revoked"` 而不是真实原因。

**退出条件**：`Store` 接口有 `getRevoke(handle): Promise<{reason, at} | null>`；`checkRevoked` 不出现任何 `as MemoryStore`。

### B5 · `better-sqlite3` 被 pin 但从无实现

**证据**：`archive/PLAN-v1-2026-10.md:9`（技术栈）、`:138`（依赖 pin）、`:144`（类型 pin）；全篇没有 `SQLiteStore` 的实现，只有 compose 里的 `SQLITE_PATH` 环境变量（`:352`）。

**后果**：CLI 多进程调用时状态不存活。`handoffpack pack` 建一张 pack，`handoffpack deliver` 是另一个进程，内存里的 `lc.packs` 已经没了。demo 走 HTTP 单进程所以看不出来，CLI 一用就崩。

**为什么与论文相关**：实验运行器是 CLI 驱动的，每条 run 独立进程。不修这个，跑不完主网格。

**退出条件**：跨进程 `handoffpack pack && handoffpack deliver` 成功；`better-sqlite3` 要么有实现，要么从依赖里删掉（删掉是合法选择，但 compose 里的 `SQLITE_PATH` 要一起删）。

### B6 · 场景编号 `s03` 被三个不同场景复用

**证据**：`archive/PLAN-v1-2026-10.md:835`、`:985`、`:1365`。

| 行号 | 场景名 | 内容 |
|---|---|---|
| 835 | `s03: mint and verify` | 签发与验签 |
| 985 | `s03: narrow` | 收窄 token |
| 1365 | `s03: sender revokes mid-task` | 任务中途撤销 |

**后果**：`tests/s03.test.ts` 会被覆盖三次，最后一个赢。`make verify` 的"10 个场景"实际跑不到 10 个不同的场景。文件名与 `spec/HANDOFF-PACK-SPEC.md` 的场景编号也对不上。

**退出条件**：10 个场景编号唯一且与 spec 一致；`make verify` 输出能逐个点名 s01 到 s10。

## 五、C 层：质量缺陷

### C1 · `s10` 号称重放攻击测试，实际是撤销测试

**证据**：`archive/PLAN-v1-2026-10.md:2232-2258`。测试体里没有任何 nonce、没有 `jti`、没有第二次使用。它只是"撤销后再调用一次应该失败"，这正是 s03 类场景。

**后果**：攻击 A3（撤销后重放）实际上没有被测试。计划 `:2106` 宣称"三个攻击被拦"，实际只测了两个半。

**退出条件**：同一张 pack 在撤销后**重新投递**必须因 `jti` 已消费而失败；测试里出现 nonce 或 `jti`。

### C2 · demo 的撤销按钮必然 404

**证据**：客户端 `:2976` 与服务端 `:2548-2557`。

```typescript
// 客户端传的是 packId
fetch(`${base}/revoke/${encodeURIComponent(packId)}?reason=by_alice`, {method:"POST"})

// 服务端按 revoke_handle 匹配，循环不命中就 404
app.post("/revoke/:handle", async (c) => {
  for (const [id, entry] of lc.packs) {
    if (entry.pack.revoke_handle === handle) { ... }
  }
  return c.json({ ok: false, error: "handle not found" }, 404);
});
```

**可观察症状**：打开 demo，点 Revoke，一定得到 `handle not found`。这不是竞态，是确定性的。

**为什么保留在 C 层**：demo 是 Demo Day 和 README 三分钟上手的载体，但不影响实验数据。

**退出条件**：点按钮后接收方下一次调用返回 `{"ok":false,"error":"by_alice"}`，这是 `:3076` 原本写下的验收语句。

### C3 · 归档计划的 `verify` 结构与新 spec 冲突

**证据**：归档计划全篇用 `verify: { check, expected }`（`:633`、`:1341`、`:1530` 等）；`spec/MSG-DESIGN-SPEC.md` 定义的是 `verify.statement` 与 `verify.predicate: { kind, args }` 两段渲染，且 `predicate` 只给 `C` 用。

**裁决**：以新 spec 为准，归档计划的 `verify` 结构作废。写 `src/schema.ts` 时直接实现 spec 的版本，不要照抄归档计划。

## 六、新模块设计

三臂与成本计量的接口细节以 `spec/MSG-DESIGN-SPEC.md` 为准，本节只给目录与依赖方向。

```
src/
├── token.ts              A1 修复后的链式凭证（macaroon 式）
├── schema.ts             Pack / Token / Verify（按新 spec，含 verify 双渲染）
├── revoke.ts             Store 接口 + MemoryStore + SQLiteStore（B4、B5）
├── lifecycle.ts          6 态生命周期
├── designs/
│   ├── free-text.ts      F 臂：encode 出散文，decode 有损
│   ├── structured.ts     S 臂：JSON + zod 校验
│   ├── contract.ts       C 臂：S + token + 强制门禁
│   └── render-to-prose.ts A2：纯函数，公平性闸门
└── cost/
    ├── meter.ts          四成分采集，token / 美元 / 秒 三币种
    └── components.ts     各成分的信号定义（对应 COORDINATION-COST-SPEC）
```

**依赖方向**（不可逆）：`designs/` 依赖 `schema.ts` 与 `token.ts`，不依赖 `lifecycle.ts`；`cost/` 依赖 `designs/` 的 decode 结果，不反向调用。保持这条线，`analysis/` 才可以离线只读 JSONL 重放。

## 八、验收方式

```bash
make verify        # 10 个场景，逐个点名
make attacks       # A1/A2/A3 三个攻击，其中 A3 是真重放
make test          # 只跑单元测试，与上面两条文件列表不同
make demo          # 点 Revoke 后接收方下一次调用失败
```

四条命令必须真的不同。如果 `make test` 和 `make verify` 输出相同，那门禁是假的（B2 未修）。
